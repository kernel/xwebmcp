# whatsapp.com

Sidebar tools and unsent message preparation for WhatsApp Web (https://web.whatsapp.com/), the browser client of an account that its owner has already linked to the browser.

| tool               | file                                           | status | notes |
|--------------------|------------------------------------------------|--------|-------|
| get_session_status | [get_session_status.js](get_session_status.js) | draft  | `logged_in`, `logged_out` (QR / linking screen) or `unknown`, from the page's own markup |
| list_chats         | [list_chats.js](list_chats.js)                 | draft  | Titles and sidebar time text of the rendered chat rows; never opens a chat or reads previews |
| prepare_message    | [prepare_message.js](prepare_message.js)       | draft  | Exact recipient and text in an unopened click-to-chat handoff; no saved draft or send |
| search_chats       | [search_chats.js](search_chats.js)             | draft  | Types into the sidebar search box, reads matching chat titles, empties the box again |

## Native WebMCP tools

None. Checked on 2026-09-29 on the logged-out QR page and on the linked, loaded client. Rechecked on the linked client on 2026-09-30 before registration: discovery returned no tools.

## URL patterns

All four tools use `["https://web.whatsapp.com/*"]` instead of the default whole-domain patterns (spec §6.2). `whatsapp.com` serves unrelated products: the marketing site and public channel pages (`www.whatsapp.com`), the Help Center (`faq.whatsapp.com`), the blog, group-invite and click-to-chat landing pages, and the WhatsApp Web client. These tools read the sidebar of the Web client and would fail or mislead on any other host, so they are attached only there. Tools for another product would need their own host patterns.

## Scope and loading

- Every tool is `kind: "page"`: it reads and, for `search_chats`, briefly edits the sidebar of the document it is registered on and never navigates. WhatsApp Web keeps one URL for all of its views, so the tools stay registered and run in place. Trusted input is not needed: WhatsApp Web accepted an untrusted `input` event on its search box on 2026-09-29, which is why `search_chats` is not `cdp` (cdp-tools.md §2.4). If a later version requires trusted input, `search_chats` reports `timeout` and would then need a `cdp` re-design.
- The tools never link a device. Linking needs the account owner to scan the QR code with their phone; `get_session_status` only reports that the QR screen is showing. They do not say which account is linked.
- No tool opens a chat or sends a message. The only page edit is `search_chats` typing into the sidebar search box and emptying it again; it never presses Enter. It refuses to run (`search_active`) when the box already contains text, and it reports `search_cleared` so a caller knows whether the sidebar was confirmed back to its normal list. Its `readOnlyHint` is `false` because it changes the search UI, even though it attempts to restore it.
- Cancelling a `search_chats` call returns `error_kind: "cancelled"` after the box has been emptied; the clean-up can take up to three seconds. Two overlapping calls are not queued: the second sees the first one's text and returns `search_active`.
- Deliberately not read: message previews, message text, unread counts, read state, pinned / muted flags and group markers, contact names of people who have no chat, and message hits from the sidebar search. Chat titles are contact names, numbers or group names written by other people; tool descriptions and `untrustedContentHint` tell agents to treat them as data.
### Message preparation and execution boundary

`prepare_message` checks only the loaded-client / linking-screen hooks and constructs an unsent handoff using the [documented click-to-chat format](https://faq.whatsapp.com/5913398998672934), read on the public Help Center on 2026-09-30. It takes one exact international phone number and the complete message, preserves both, and returns `status: "prepared"` with an encoded `https://wa.me/<number>?text=...` link. It never requests that URL, opens a chat, fills a composer, saves a draft or sends. This is a page-local computation, not a CDP navigation or a claim that the composer was tested.

- The link is not bound to the current sending account. `account_verified` and `recipient_verified` are always `false`; the number is syntax-checked, not checked for an active WhatsApp account. No contacts, histories, account IDs or names are read to resolve the recipient.
- The owner must approve opening the link, since it can open a chat, mark incoming messages read, and prefill its composer. The owner must then verify the actual sending account, recipient and full text and send manually. Preparation is not approval, and there is no automatic navigation, follow-up execution or retry.
- The URL contains the supplied phone number and message. Treat it as private content: do not auto-preview, fetch, publish or share it. It contains no cookies or session credentials.
- Only digits, including the country code, are accepted for the recipient: 7–15 digits, nonzero first digit, no normalization. Text is limited to 2000 Unicode code points; LF newlines and spaces are preserved. Whitespace-only text, other controls, line separators, bidi overrides and unpaired surrogates fail before page access.
- No send/edit/delete/group-change or message-history tool is shipped. This runtime specifies no trusted human approval enforcement for an exact account, recipient and text. A model-supplied confirmation flag would not solve that; extra fields such as `confirmed`, `send` and `account_id` are rejected. Opening chats to discover draft/message internals also needs separate owner approval because of read receipts. No such chat was opened during this implementation.

Register the whole namespace together:

```javascript
const fs = await import("node:fs");
const names = fs.readdirSync("domains/whatsapp.com").filter(f => f.endsWith(".js")).sort();
const tools = names.flatMap(f => eval(fs.readFileSync("domains/whatsapp.com/" + f, "utf8")));
await webmcp.addCustomTools({ namespace: "whatsapp.com", tools, forceOverwriteNamespace: true });
```

## Site quirks

- All hooks are `data-testid` values and roles, not text or class names (classes are hashed): `wa-web-main-screen` and `chat-list-search-container` for a loaded client, `link_device_*` for the QR screen, `chat-list` with `role="row"` rows named `list-item-N`, `cell-frame-container`, `cell-frame-title`, `cell-frame-primary-detail`, `text-highlight`, and `search-no-chats-or-contacts-container` for an empty search. The result text is in the account's language, so the tools never match on English words.
- Chat rows carry no chat id. `position` is the rank among the returned rows, ordered by the `list-item-N` index, and is not a handle for opening a chat.
- The sidebar search lists three groups: chats (rows with a time text), address-book contacts (rows without one) and message hits (rows without a chat frame). Only the first group is returned. A sidebar search for a common letter returned all of them, which is why a returned `total` can be much smaller than what the sidebar shows.
- After typing, the sidebar first lists every old chat under a "Chats" heading, with only the matching ones highlighted, for about half a second, and then replaces it with the filtered result (plus the contacts and message groups). `search_chats` therefore treats a frame as final only when every chat it lists highlights part of the query, and then waits for the result to stay unchanged for four polls (150 ms apart); a successful search took about 1.7 s on the observed account.
- The first load of a fresh browser can sit on a blank splash for several seconds; `get_session_status` reports `unknown` then, and `wait_sec` waits for it.

## Known limitations

- `prepare_message` produces an unopened handoff only. Live composer prefilling, recipient existence, sender identity, saved drafts and delivery are unverified. Its success means only that the linked-client hooks were present and the exact input was encoded. Opening the handoff and executing any message action remain human steps with the side effects stated above.

- Only WhatsApp Web. The marketing site, Help Center, channel pages, invite links and WhatsApp Business are not covered.
- `list_chats` and `search_chats` return only rows the sidebar has rendered and do not scroll, so `limit` and `position` start at the first rendered row, which need not be the top chat if the sidebar was scrolled. `more_rows_possible` looks at the nearest ancestor whose `overflow-y` is `auto` or `scroll` (the sidebar pane on the observed account) and reports whether it overflows; `false` does not prove every chat is rendered. It was only observed on a small account whose list did not scroll, so behaviour on long, virtualized lists is unverified.
- The selected filter chip (All, Unread, Favorites, Groups) exposes no machine-readable state, so it cannot be detected. With a filter other than All the sidebar, and every result, contains only those chats.
- `search_chats` decides that a row is a chat by the time text next to it. That matches every chat and no contact observed so far. A chat without a time text would be skipped; archived chats were not tested.
- The rule that a result is final once every listed chat highlights part of the query held for every title query observed. A chat that the sidebar lists without any highlight (for example a match on text the sidebar does not highlight) keeps the result unsettled and ends in `timeout`, not in a guessed result. Chats matched through other text in the row (such as a group member's name) are only covered by fixtures.
- `search_chats` can return part of the result as `ok` if the sidebar shows a frame that lists only some of the matches and keeps it unchanged for about 0.6 s or longer: a result that fills in progressively, or a windowed sidebar whose first frame lacks rows and lasts about 0.75 s or longer. Neither was seen on the real site, which lists all old chats first. `total` is the number of chats in the frame the tool settled on, not a count from the site. A frame with a heading and no chat rows counts as final, so a Contacts group that appeared more than 0.6 s before the Chats group would produce a wrong `no_results`.
- The timing constants (four unchanged polls 150 ms apart, default 8 s timeout) come from a handful of observations on one account, and browsers throttle timers in background tabs to about one second, so a short `timeout_sec` in a hidden tab can end in `timeout`; treat that outcome as unknown.
- `search_chats` keeps the search box it found at the start. If the site replaces that element during a search, the tool cannot empty the new one and reports `search_cleared: false`. On an account with no chats it can still settle on a contacts-only result but cannot confirm the list is back to normal, so `search_cleared` is `false`.
- Query rules: 1 to 100 characters counted as code points after trimming, and control, line-separator and bidirectional-override characters and unpaired surrogates are rejected. Other invisible characters, such as zero-width and joiner characters, are typed as given.
- Unobserved: the states "phone offline", "use here" conflict, session-expired banners and the progress screen shown right after linking (all report `unknown` or, if the chat list is present, `logged_in`); unread badges, pinned and muted markup; group versus one-to-one detection; chats with no messages; the empty-account case (reported as `not_ready` because a not-yet-loaded list looks the same); non-English UI language.
- The extension runtime was only exercised by an independent reviewer on the logged-out QR page and on a fabricated sidebar (see QA summary). The web.whatsapp.com page sets a content security policy without `unsafe-eval`, so the extension registers page tools there through its CDP fallback (cdp-tools.md §9.12); authenticated use through the extension is unverified.
- Policy note: WhatsApp's Terms of Service (https://www.whatsapp.com/legal/terms-of-service, effective date January 4, 2021 as read on 2026-09-29) require use for "legal, authorized, and acceptable purposes" and prohibit, under "Legal And Acceptable Use", bulk messaging, auto-messaging, auto-dialing and "any non-personal use" unless authorized, and, under "Harm To WhatsApp Or Our Users", accessing or collecting user information through automated means in impermissible or unauthorized ways. These tools read an account owner's own, already-linked browser session, and `search_chats` only types into the sidebar search box and empties it again; no message execution, chat-opening or bulk-collection tool is provided. Unsent click-to-chat preparation is provided without opening its link. This repository makes no determination about whether a particular use complies with those terms.

## QA summary

Every tool stays `draft`. The prior review below identifies older sources and is not sign-off on the current source: null-input handling and the search annotation have changed, and `prepare_message` is new. Current-source QA is recorded separately below; no independent authenticated run exists.

- `tests/whatsapp-session-status.test.mjs` and `tests/whatsapp-chats.test.mjs` run the tool sources against a fabricated sidebar (`tests/fixtures/whatsapp/app.mjs`) on a virtual clock. The fixture reproduces the frames the real sidebar showed after typing (old rows with the matches highlighted, then the filtered result) and adds blank, late-filling, long-lasting, shorter-than-normal and order-swapping variants. The tests cover success, sidebar ordering, truncation, every error kind, malformed and Unicode input, empty and unmatched searches, timeouts and cancellation, focus restoration and the scroll-container checks, and check each result against its `outputSchema`.
- Read guards: the fixture records any read of message previews, contact names and message hits (by `textContent`, `getAttribute`, or a `[name]`, `[name="v"]` or `[name^="v"]` selector that returns them; any other attribute syntax throws) and gives the tools a strict element view that records and throws on any member they have no reason to use (`innerText`, `innerHTML`, `dataset`, `attributes` and the like). A selector that returns no forbidden node is not recorded. The tests require zero recorded reads and no event other than the two search-box `input` events, and a self-test shows the guards fire. The fixture models no unread, pinned or muted markup, so that those are not read is a property of the sources, not of a test. A static test rejects clicks, key events, network, storage, scrolling and navigation in the sources. Deliberately broken copies of the sources (dozens of variants) are each caught by at least one test, except one equivalent variant that starts the scroll-container search at the list itself, which behaves the same on the observed page.
- Independent review (a separate agent, `agt_739c76521225a0c3ead9`). Its first pass found two blocking defects: a stale-frame guard that compared row counts, and read guards with blind spots. The guard was replaced by a finality rule with a narrower partial-result mode, listed under Known limitations, and the read guards were widened (with the limits stated above). It then signed off (PASS) with no blocking defects on the sources whose SHA-256 prefixes are `a342ba6f` (`get_session_status`), `8e2723a8` (`list_chats`) and `3ba2b408` (`search_chats`); editing any of them makes that sign-off stale. Across three rounds it ran dozens of deliberately broken copies of the sources, the validator and full suite, and Ajv strict compilation of the schemas.
  - Logged-out surface only, on a Kernel browser: whole-namespace registration, URL matching, `not_authenticated`, invalid input, `wrong_page` on other origins, and the page left unchanged. `unknown` and `not_ready` were checked on an artificial splash page made by blocking the site's asset host in its own browser.
  - In Chromium, the real sources against a fabricated sidebar served on the site's origin by intercepting its own browser's request (so not WhatsApp's markup): a scrollable list, old frames lasting 0.5 to 3 s, contacts-only and 25-match queries, with exactly two untrusted `input` events per search, the box emptied, focus restored and no click or key events.
  - In the local Chrome extension (Chromium 153 headless): the extension code was unmodified, but a scratch copy of the manifest had the site permission added because headless has no grant popup, a non-headless user agent was used because WhatsApp serves an unsupported-browser page to headless Chrome, and invocation went through the extension's MCP `invoke_tool` with `allow_user_tabs`. The tools registered; on the QR page `get_session_status` returned `logged_out` and `list_chats` and `search_chats` returned `not_authenticated`; on the fabricated sidebar under a content security policy without `unsafe-eval` they also registered and returned correct results (that this went through the CDP fallback is inferred from the policy and the extension code, not traced).
  - These are single-run observations, not a parity claim, and nothing on an authenticated account was independently exercised.
- Live, 2026-09-29, author only, on a Kernel browser holding one user-linked account with a handful of chats (only result shapes were inspected; no names, numbers or message text were recorded): the namespace registered atomically; `get_session_status` returned `logged_in`; `list_chats` returned every rendered row, and `limit` truncation and validation errors behaved as specified; `search_chats` returned title matches, left out the address-book contacts that the sidebar also listed for a one-letter query, reported `no_results` for a query no chat matched and for a query that only appears in message text, trimmed the query, accepted a 60-emoji query, and left the search box empty, unfocused and showing the normal chat list each time. With text placed in the search box by the author, both `list_chats` and `search_chats` returned `search_active` and left that text untouched.
- On a fresh browser showing the logged-out QR screen (nothing clicked or entered), `get_session_status` returned `logged_out`, `list_chats` and `search_chats` returned `not_authenticated`, and the tools were not listed on `www.whatsapp.com`.
- Not live-checked: `not_ready`, `timeout` and `site_changed` against the real site (fixtures only, apart from the artificial splash page above), authenticated use through the Chrome extension, and any account other than the one above.
- Authenticated sidebar success and timing still need an independent owner-authorized run. `qa_passed` requires independent success/failure coverage of the final source; `verified` additionally needs the dated live invocation required by spec §5.4. Historical observations do not establish those statuses for changed sources.
